来源：用户在 R116 之后亲自试玩，共 11 项。Claude 负责计划、审查、提交；Codex 实现与验证。
基准提交 `409574d`。按批次推进，每批审查通过后由 Claude 提交推送。

## 工作约定（每批都适用）

- **Codex 不做任何 git 写操作**（commit/push/stash/checkout -b 等），只读 git 可以用。
- 图形客户端：`DISPLAY=:0`（禁止 `:1`），并加 `LIBGL_ALWAYS_SOFTWARE=1`（virgl 会让 Flywheel 崩）。DevClient 命令返回 success 不代表结果正确，要看实际状态/截图。
- 验证要和改动相称：定向 JUnit/GameTest + 视觉项的截图（第一人称/第三人称）；每批结束跑一次全量 `build runGameTestServer`。不需要上一批森林泉那样的重型证据协议；证据放 `evidence/r117-<批次>/`，一个简短 README 写清改了什么、怎么验证、截图在哪。

## 批次 A — 玩法逻辑（小而清晰）

### A1（原 #4）解锁矛/锤时自动给一份道具
现状：武器靠技能界面里的“领取”按钮（`SpiritProgress.claimedWeapons`，`SpiritScreen` 第 ~153 行）。用户期望解锁当下就拿到。
要求：解锁 SPEAR/HAMMER（含 `/ori unlock`）时直接放入背包，背包满则掉在脚下，并标记 claimed；解锁自动发放即消耗终身一次领取并置 claimed 位；领取按钮仅用于更新前已解锁但未领取的老存档，不提供丢失后的补领。矛、锤、弓均纳入 claimedWeapons，旧存档兼容。

### A2（原 #6）光矛没能量时按住右键鬼畜
现状：能量不足时按住右键，客户端反复播放投掷预测动作，手臂抽搐。
要求：能量不足或冷却中时客户端不播放投掷/蓄势动作，手臂保持持握姿态；给一次性反馈（HUD 能量条闪一下 + 轻提示音），按住不重复刷。服务端拒绝逻辑不变。检查锤子蓄力、弓是否有同类问题，一并修。

### A3（原 #8）Boss 祭坛冷却
现状：`GloomAltarBlock` / `StormAltarBlock` 的 `useWithoutItem` 打完 Boss 可以立刻再召唤。
要求：每个祭坛方块独立冷却（存在方块实体里，跨重载保持）。Boss 被击败后 **一个 MC 日（24000 tick）** 内不能再召唤；Boss 存活时也不能叠召第二只（若已有守卫就沿用）。右键时显示剩余时间（actionbar，中英文 lang 对齐），冷却中祭坛粒子熄灭/变暗作为视觉提示。数值放到规则类里，有 JUnit。

### A4（原 #3）攀爬白名单
现状：`SpiritMovement` 里 WALL_SLIDE + `climbing(...)` 对任何墙生效。
决定：
- 新增方块标签 `orimod:spirit_climbable`（数据驱动，整合包可扩展），默认包含：`#minecraft:logs`、`#minecraft:leaves`、`#minecraft:climbable`（梯子/藤蔓/脚手架等）、蘑菇柄、竹子、苔藓块、本模组的灵木/金索木/大灵树根木/灵藤/根唇等木质与藤蔓类方块。
- **攀爬（CLIMB 向上爬）** 和 **STICKY 碎片的贴墙** 只对标签内方块生效。
- **蹬墙跳 / 墙面下滑** 仍对任何实心墙生效（MC 里跳墙不该被白名单卡死）。
- 判定用玩家面前实际接触的那几格（脚、身中、头）里任一命中标签即可。有 JUnit/GameTest：石墙不能爬、原木能爬、蹬墙跳在石墙上仍可用。

### A5（原 #10）锤子下砸加速
现状：从灵树顶一路下砸，速度恒定“太圆滑”。
要求：下砸（stomp/smash 下落阶段，看 `HammerSlam` 与移动层）改为持续加速：起始速度保持现值，每 tick 加速，直到一个终端速度（建议约为现在的 2.5–3 倍，以不穿方块为准）。落地冲击（伤害/范围/镜头震动/粒子）随下落高度或末速度适度放大并封顶。仍然无摔落伤害。数值进规则类并有 JUnit。

## 批次 B — 第一人称与视觉

### B1（原 #1）第一人称手部模型和动作开倒车
用户原话：“手部的模型，以及动作，完全的开倒车；目前第一人称的动作完全没了；持有武器的时候，这是什么架势？为了展示而展示吗？而且更僵硬了”。
背景：B3 两次提交 `e5a870c`、`fbd5e9f` 把空手/方块/刃/弓/锤/矛换成了双骨手臂（`SpiritArmRig`、`SpiritWeaponRig`、`SpiritFirstPerson*`），锤/矛按“屏幕中心 60px 内”对齐 mace/trident 做尺寸，导致武器像展台一样摆在画面中央。
要求：
1. 先取证：在 `5d151ec`（B3 之前）与 HEAD 各拍同一组第一人称动作序列（静止、走、疾跑、跳、挥击/攻击、使用物品、切换物品、每种武器的待机与动作），列出哪些动作在 HEAD 消失或变僵硬（行走晃动、视角摆动滞后、挥手、装备下沉/抬起、攻击挥动等）。可用 worktree 或拷贝目录跑旧版本，不要在主工作区 checkout。
2. 恢复所有丢失的动作：手臂要跟随原版的 bob / 视角摆动 / swing / equip 进度，空手和方块的挥击要有完整挥动。
3. 武器待机姿态改成“握在手里”的自然持握：位置靠画面右下（参考原版持剑/三叉戟在右下的位置与比例），不居中展示；锤子扛握或斜持，矛斜持矛尖朝前上；动作（蓄力、投掷、挥砸）从这个自然姿态出发再回到它。
4. 遵循 `first-person-pose-tuning` 经验：pitch 在第一人称几乎看不出，用高度、roll、yaw 来表达姿态；贴近镜头的爪子会占满画面；爪子朝向取自完整物品旋转。
5. 交付截图对比表（旧 / 新 每种动作若干帧），由 Claude 审图。

后续确认（B1）：swing/equip/bob 和使用动画全部以原版 `ItemInHandRenderer` 为基准，爪子只替换外观并贴合物品；精灵武器 idle 的大小与可见握点按 `5d151ec`，写入物品 JSON 的第一人称 display，不沿用旧版相机空间补偿。对比增加关闭精灵形态的原版人形，空手及四种武器左键攻击各交付 swing 0→1 的六帧条带。光矛改为按住举矛、松开发射（原版三叉戟 `SPEAR` 动画），最短举矛 4 tick；快速点按补满 4 tick 后自动投出。按下时能量或冷却不足沿用 A2 拒绝锁存，不举矛；服务端在实际发射时才扣能量、生成投矛。中途切物品或打开界面取消，不扣能量。附对应 JUnit/GameTest。

### B2（原 #2）滑翔羽毛握法
用户期望：羽毛 **横着** 举在头顶上方，**左手握羽毛尖、右手握羽毛杆**（羽轴从右手指向左手，羽片横跨头顶）。现在是竖着拿，不对。
现状：`FeatherPose.matrix` 把长轴设为向身后上扬 20° 拖在身后，两手连线只决定 bank。
要求：长轴改为沿玩家左右方向（从右手=羽根到左手=羽尖），羽片面大致水平略前倾，位于头顶上方，两手举起握住两端；第三人称和第一人称（若可见）都要对。左右要按玩家主手设置正确镜像（左撇子时可以镜像，但默认右手主手时必须是右手杆左手尖）。附侧视、正视、俯视截图。

实现补充（B2）：羽毛保持资产原长 1.35 格及宽厚比例，禁止按手距缩短；右手握裸羽杆（轴向 0.12 格处），左手握外侧羽轴（1.02 格处），尖端在左手外伸出约 0.33 格。同步重烘焙 glide / glide_open / glide_close，抬肩、展开双臂适配固定握点，保持手臂骨长和掌指比例，羽片位于耳朵上方；主手为左时镜像。角色 v017 仅这三个动画通道集合变化，其余 99 个动画、网格及静止骨架保持原数据。

相关代码：`GinsoEscapeLayout`（HEART=(0,94,0)，exitHeight=treeHeight-11）、`GinsoEscape`、`GinsoWaterHeartBlock`、`GinsoFloodSurface`、`GinsoWaterRenderType`、`client/GinsoEscapeClient`。

4. 布局改动需要版本化：新生成的金索树用新版本；已生成的旧树要么保持可玩，要么安全迁移，说明你的选择。

## 批次 D — 腐化生态（原 #11，最大的一项）

用户原话：“腐化看着太可怜、太寒蝉，就这么一丁点，里面啥用没有。能不能改成一个生态，会自动蔓延，只有摧毁腐化之核才能终止？同时看不出腐化造成了什么影响，比如让里面的动物发生变化（类似原作磨坊的 Boss 战那样），或者其他的。”
相关：`BlightData`、`BlightedGroundsFeature/Shape`、`BlightRules`、`BlightSearch`、`GloomCoreBlock(Entity)`、`GloomThornsBlock`、`GloomWaterBlock`、`Restoration*`、各 Gloom 生物。

设计（Claude 定）：
1. **生态与蔓延**：每个腐化之核是一片活的腐化区。核心在加载状态下按节拍向外蔓延：每次在当前边界外随机挑少量自然地表格转化（草/土→腐化土，花草→枯萎或移除，树叶→枯叶/掉色变体，小水池→腐水），形成不规则、有触须感的边界；半径从初始约 12 格逐步长到上限（建议 48 格），速度为“一个游戏日能明显看出扩张”。每 tick 读写预算有上限，只在已加载区块，不同步加载区块；遇到庇护所（现有 SANCTUARY_RADIUS）、玩家建筑方块（非自然方块）、结构保护区一律不转化。
2. **区内影响**（让人一眼看出“被腐化了”）：
   - 环境：腐化土、荆棘、腐水、枯木装饰；区内天色/雾气偏暗紫（客户端按到核心距离渐变），环境粒子。
   - 动物：区内的原版被动动物（牛、猪、羊、鸡、兔等）会被“腐化”——变为暗紫着色、眼睛发光、主动攻击玩家的腐化变体（或换成对应的 Gloom 生物），掉落物变为腐化材料。离开区域不会自动恢复，只有核心被摧毁后恢复成原动物。
   - 怪物：区内刷出腐化生物（沿用现有 Gloom 甲虫/喷吐者/鹰等）概率提升。
   - 玩家：区内自然回血停止、能量缓慢流失（精灵形态），给出明确 HUD/提示。
3. **终止与净化**：只有摧毁腐化之核能停止蔓延；摧毁后区域按现有 Restoration 逻辑从核心向外逐步复原（腐化土→草，枯叶→正常，腐化动物→原动物），奖励随区域大小适度提高。
4. **持久化与兼容**：区域状态（核心、当前半径、已转化计数）存在 SavedData；已有的小块腐化地按新规则在下次加载时开始蔓延或保持原样（说明你的选择）。
5. **可配置**：服务器配置可关闭蔓延或调整速度/上限（有人不想被蔓延吞家）。

要求 Codex：**先回一份实现方案**（文件/类划分、蔓延算法和预算、动物腐化的实现方式、迁移策略、测试计划），Claude 审完再动手。实现后：GameTest 覆盖蔓延边界与保护、动物腐化与恢复、核心摧毁后停止并复原；实机截图（初始、一天后、动物被腐化、摧毁后复原中）。
